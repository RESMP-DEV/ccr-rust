The router is split into three cooperating layers. `src/router/mod.rs` exposes the HTTP handlers (`handle_chat_completions`, `handle_responses`) and the `execute_attempt` loop that builds per-tier requests, applies admission control via `state.admission_tracker`, launches primary + hedge attempts on `tokio::select!`, and records metrics through shared `crate::metrics` functions. `src/routing.rs` provides the EWMA tracker (`EwmaTracker`) that reorders configured tiers by recent latency (with min-sample fallback to config order). `src/gp_router.rs` provides an optional Gaussian-process surrogate (`GpRequestRouter`) that reranks tier order using request features (prompt size, token estimate, hour-of-day, active streams) via Thompson sampling / UCB acquisition strategies; it falls back to the EWMA-ordered list while unfitted. The top-level `router/mod.rs` wires these together: after selecting a base tier order (config or EWMA), it optionally invokes `GpRequestRouter::plan_rerank` before dispatching, then runs the retry/hedge loop against the final ordered list. Cross-cutting concerns—usage normalization, reasoning controls, OpenAI compatibility headers, and Responses API passthrough—are layered as modules under `router/` that wrap the same underlying attempt execution.
