# GLM-5.4 cutover and capability cutoff: 2026-11-23

## Scope

Force every governed CCR lane onto GLM-5.4, close the path that was still
serving GLM-5.3, and define the release-handoff cutoff that separates
pre-GLM-5.4 measurements from post-cutover ones.

## The hole that survived the 2026-11-23 supersession

The earlier deployment made `zai,glm-5.4` the advertised model everywhere, but
`Provider.models` is an advertisement, not an access control. A client that
names a provider and a model explicitly is dispatched to that provider with
that model id on the wire, so the retired ids kept working. Measured on
`http://127.0.0.1:3456` before the cutover, with the upstream reporting
reasoning tokens, so each answer came from the named model:

| Requested | Upstream model | Upstream reasoning tokens |
| --- | --- | --- |
| `zai,glm-5.3` | `glm-5.3` | 3 |
| `zai,glm-5.3-flash` | `glm-5.3-flash` | 31 |
| `zai,glm-5.2` | `glm-5.2` | 6 |
| `zai,not-a-model` | n/a | tier failure, no answer |
| `glm-5.3` (bare id) | `glm-5.4` | n/a |

A live consumer was on the retired model: the OCR review poller ran
`ocr-v1.12.9 review --provider ccr-glm --model zai,glm-5.3-flash` against the
OCR listener on `:3458` with concurrency 4, and the CCR log recorded
`Rate limited, backing off tier=zai,glm-5.3` while the same lane also answered
other traffic.

**The cutoff rule.** A measurement is *pre-cutover* if any of its runs were
served by a GLM-5.3-family model, and *post-cutover* otherwise. Post-cutover
runs are also the only ones whose requests can be assumed to have reached the
upstream as `glm-5.4`; before the cutover a request naming a retired id was
served by that retired model even when the client asked for `glm-5.4` by
default. Scores from the two cohorts are not comparable: the pre-cutover
cohort measured a different model family on the same prompt bytes.

## Change set

### Router

- `src/config/types.rs`: new `Provider.model_map`, a `HashMap<String, String>`
  deserialized from the JSON key `modelMap`, mapping a requested model id onto
  the upstream model id that provider serves.
- `src/router/dispatch.rs`: `canonical_model_name` consults the provider map
  before the built-in MiniMax M3 pinning, so the map wins over every built-in
  rule. That function is the single place the wire model id is chosen for the
  OpenAI passthrough, the Anthropic-compatible, and the Responses protocol
  paths, so one change covers all three, streaming and non-streaming.
- `src/config/mod.rs`: `validate_provider_contracts` rejects a map target that
  the provider does not list in `models`, and rejects an entry that maps a
  model onto itself. Both are load-time configuration errors.
- `tests/test_provider_model_map.rs` (new): four integration tests with a mock
  upstream that records the `model` field it received.

### Policy

- `scripts/ccr_fallback_policy.py`: every consumer primary is now
  `zai,glm-5.4`. The scoped worker drops its MiniMax primary and the OCR lane
  drops its OpenRouter primary; MiniMax and OpenRouter remain in the shared
  chain and as a direct-only seat, so a Z.AI window exhaustion degrades a lane
  instead of ending it.
- The `zai` provider carries
  `"modelMap": {"glm-5.3": "glm-5.4", "glm-5.3-flash": "glm-5.4", "glm-5.3-flashx": "glm-5.4"}`.
- The machine policy integrity pin was recomputed to
  `7dd4d9ad8d646f7aa9f5a4cd39858f702741d6c5efddd42b902f13a94b9852b3`.

### Consumer pin

- `/Users/kearm/ocr-poller/ocr-pr-poller.sh`: the `glm-5-3-flashx` review
  profile now pins `zai,glm-5.4` and labels itself `GLM-5.4 / xhigh / CCR`.
  The profile name is unchanged because it keys the state and cache
  directories. The provider model map makes this pin correct even if a stale
  copy of the script still names the retired id.

## Provider state at cutover

At the cutover moment the Z.AI coding plan was inside its rolling 5-hour
usage window, so no GLM model could be served, on either the old or the new
route. Measured directly against the Z.AI Responses endpoint with the same
credential the router uses, for both `glm-5.4` and `glm-5.3`:

```
HTTP=429
{"error":{"code":"rate_limit_exceeded","message":"Usage limit reached for 5
hour. Your limit will reset at 2026-11-23 17:08:16", ...}}
```

The reset time is displayed in the provider's own timezone (UTC+8), which is
2026-11-23 09:08 UTC, 2026-11-23 01:08 PDT. While the window is closed the
lanes fall through to MiniMax M3.1 Flash, which is what the live probes
observed: a request for `zai,glm-5.4` returned a `MiniMax-M3.1-Flash` body,
and the CCR log recorded `Rate limited, backing off tier=zai,glm-5.3`.

### Window reset and the measurement window

The window reset at the time the provider quoted. A direct probe against the

### Observability gap found while measuring

The router's log is honest on the governed path and misleading on the direct
path:

- Governed path (a bare model id that resolves to the default route): the log
  shows the resolved model, `Incoming request for model: glm-5.3` then `Trying
  zai,glm-5.4 (zai)`. The alias is visible.
- Direct path (a client pins `provider,model` and that pair is not in the tier
  list): the log echoes the requested label, `Direct routing: zai,glm-5.3 (not
  in tier list)` then `Trying zai,glm-5.3 (zai)`, while the upstream actually
  received `glm-5.4`. The wire is right and the log is wrong.

The isolated measurement lane took the direct path, which is why its log alone
cannot prove the alias; the proof there is the upstream's echoed `model` field
or a recording upstream, as in "Live verification" and the tables above. The
resolver that performs the mapping is `canonical_model_name` at
`src/router/dispatch.rs:332`, and it logs nothing; the log site is
`src/router/mod.rs:779`. Closing the gap means changing one of those two files,
and the repo sits exactly at its `TOTAL_CEILING` of 41,372 nonblank Rust lines
(`python3 scripts/check_sloc.py` reports `41372/41372`), so the direct-path log
line is recorded here rather than patched.

### Live-lane serving reality: the alias is not the whole answer

The alias guarantees no GLM-5.3 is served. It does not guarantee a GLM-5.4
answer, because the governed chain continues past `zai` when the provider
rejects a request or the route is saturated. Counters from `:3456` `/metrics` at
2026-11-23 01:41 PDT, 56 minutes after that listener started:

| Counter | Value |
| --- | --- |
| Codex requests served | 338 |
| Dispatches to `zai` | 144 |
| Dispatches to `minimax` | 200 |
| `rate_limited` failures on `zai` | 81 |
| AIMD limit `zai,glm-5.4` | 5 (2 at 01:35) |
| AIMD limit `minimax,MiniMax-M3.1-Flash` | 64 |
| Input tokens `zai` / `minimax` | 18.56 M / 26.96 M |
| Requests held on admission | 11, 660 s total wait |

Tier dispatches sum above the request count because a request that falls back
is dispatched once per tier, so one Codex request can account for a `zai`
dispatch and a `minimax` dispatch.

So 200 of 344 tier dispatches, 58%, were answered by MiniMax M3.1 Flash rather
than GLM-5.4. The mechanism is AIMD admission: an unconfigured route starts at
`DEFAULT_INITIAL_LIMIT` 8 and may grow to `DEFAULT_MAX_LIMIT` 64
(`src/admission.rs:32`), but every rate-limit rejection cuts it, and the 81
rejections held `zai,glm-5.4` at 2 concurrent slots at 01:35 before it grew back
to 5. `minimax` sat at its 64 ceiling, so a request that finds `zai` saturated
is admitted on `minimax` immediately while `zai` defers it to the end of the
pass (`src/router/mod.rs:670`). The rate limits track request size, not
concurrency: four parallel small direct probes to the provider all returned
HTTP 200, while dispatches that got a 429 carried a median of 191,474 input
tokens against 144,479 for those that succeeded, and the live `loc-infra`
session carries a 260k-token context.

The practical consequence: the old sessions are no longer served GLM-5.3, but a
majority of their answers are MiniMax M3.1 Flash rather than GLM-5.4. That is
pre-existing chain and admission behaviour, not something the cutover
introduced, and it is a policy question rather than a defect: keeping MiniMax in
the main lane's chain trades answer availability for answer identity.

## Non-claims

- This receipt does not claim GLM-5.4 is better or worse than any other
  model. It records routing, alias, and deployment state.
- It does not claim the retired ids can no longer be *named*. They are still
  accepted and are aliased onto GLM-5.4; what cannot happen any more is the
  retired model being served.
- It does not claim the Z.AI plan was healthy at the cutover moment. The
  5-hour window was exhausted then, so the cutover-time live probes were
  answered by a fallback tier. The window has since reset, and the
  post-cutover capability measurement above ran clean on `zai`.
- It does not claim the OCR poller test suite is green. 25 of its tests fail
  with exit code 75 both with and without the pin change, which was verified
  by stashing the change; the failures are pre-existing and unrelated.
- It does not claim the other running Codex sessions were restarted. They
  keep the model pin they read at process start.
